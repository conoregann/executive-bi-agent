# User access contract

The local runtime serves one fictional company. Operators provision named users as `admin` or `restricted`; restricted users have explicit customer ID grants. There is no self-service signup or tenant selection. The API process uses writable `DATABASE_URL` for identity and investigation persistence, while analytics continue through the dedicated read-only role.

`POST /v1/sessions` accepts JSON `{ "username": "alice", "password": "..." }`. Valid credentials for an active user issue a random 43-character session token with an eight-hour expiry. Only its SHA-256 hash is persisted. Passwords use per-user salted scrypt hashes. The browser keeps session and investigation tokens in memory; reload or sign-out clears browser access. An inactive user cannot create a session or use an existing one.

Every investigation endpoint, including question resolution, requires `X-Session-Token`. The investigation bearer token is a second credential for stored resources; it does not identify a user. A stored investigation is bound to its creating user. Both credentials are checked for record, answer, evidence and follow-up access. Missing/expired sessions return `401`; another user's investigation returns `404`. Older unowned records are not available through the authenticated runtime.

The request field `permittedCustomerIds` is retained for wire compatibility but is only a requested filter. For a restricted user, omitted IDs resolve to the user's current grant list. Explicit IDs must all be granted or the request returns `403` before tool execution. An admin may request all customers by omitting IDs. A restricted user with no grants cannot create an investigation. The resolved IDs are retained in the record and passed unchanged to every metric, document and operational tool.

On every protected read and follow-up, the server reloads the user's active status and current grants. A restricted user may read a retained investigation only while all its customer IDs remain granted. Revoking one grant or deactivating the user blocks subsequent reads, including answer and evidence, even with both original tokens. Follow-ups inherit the retained scope and cannot use another user's parent.

For local setup, run `pnpm db:migrate` and build the API, then provision users with `BI_USER_PASSWORD=... DATABASE_URL=... pnpm --filter @executive-bi/api user:add -- alice restricted cust_acme`. Use `admin` with no customer IDs for a full-scope user. The command rejects duplicate usernames and grants. Operators revoke access by deleting rows from `app.user_customer_scopes` or setting `app.users.active = false`; the next request observes that change. Protect credentials and the writable database URL as application secrets. The synthetic test API factory can run without an access store for isolated legacy contract tests; the production entry point always supplies the PostgreSQL access store.
